# Zeron Block 与 Page 统一实施及阶段验收方案

日期：2026-10-05\
状态：阶段一至阶段六本地实施与当时自动验证完成，分别见 [阶段一记录](./2026-10-05-block-page-unification-stage-one.md)、[阶段二记录](./2026-10-05-block-page-unification-stage-two.md)、[阶段三记录](./2026-10-06-block-page-unification-stage-three.md)、[阶段四记录](./2026-10-06-block-page-unification-stage-four.md)、[阶段五记录](./2026-10-06-block-page-unification-stage-five.md) 和 [阶段六交付记录](./2026-10-06-block-page-unification-stage-six.md)。后续组件 API 以 [状态组件收敛记录](./2026-10-06-feedback-component-consolidation.md) 为准；最终 review、当前证据有效性与提交拆分见 [最终 Review 与 Commit 计划](./2026-10-06-block-page-unification-review-commit-plan.md)。人工验收仍待确认，尚未公开发布；阶段六历史安装矩阵不自动覆盖后续源码变化。

目标：在保留业务行为和现有安装能力的前提下，统一状态表达、图表设计和高频页面组合。通过少量公共能力与分批迁移，让同类信息具有一致的视觉和交互，减少重复实现。

范围基于文档交付前核对的当前工作区：文档目录中的 17 个 Block、26 个 Page，以及独立 Workflow 页面，共 44 个入口。前一轮分析为 42 个，本次核对新增了 `security-overview-01` 和 `deployment-detail-01`，已补入迁移台账。统计口径是文档集合，不是 `kind` 字段；其中存在 flow、prototype 和 layout。实施开始时应重新核对目录及未提交改动，冻结实际基线。

## 1 实施原则和完成标准

1. 优先复用现有 `Badge`、`Empty`、`Skeleton`、`InlineNotice`、`MetricCard`、`StatusOverview`、`ChartContainer`、`DataTable`、`InfoItem`、`DetailList`、`PageLayout` 和 `Container`。
2. 统一业务状态的表现方式，不合并健康、执行、发布、权限、账号等领域枚举。
3. 图表同时统一视觉与数据契约。不能以改样式为由，将缺失数据改成零、改变单位或改变汇总口径。
4. 保留既有公共 props、事件回调、受控/非受控行为和安装入口。新增能力优先采用可选属性或内部适配；确需破坏性变更时单独形成迁移说明，不混入样式整理。
5. 通用视觉能力进入 `packages/ui`；领域映射、品牌身份和工作区导航进入 `packages/blocks`；文档展示逻辑留在 `docs`。
6. 每个公共能力必须有真实消费者验证。仅把重复代码搬入文件，不算阶段完成。
7. 不改造完整业务引擎，不新增全局状态管理，不更换图表库，不将所有列表和编辑器强行合并。
8. Registry、文档和指南随阶段增量更新；最终阶段负责整体复验，不能把安装能力一直推迟到最后。

总体完成条件：44 个入口均有处理结论与证据；目标重复实现已迁移或有明确保留理由；功能、数据含义、主题与响应式检查通过；新增能力可在独立消费者中安装使用。正式公开发布另外记录，不能以本地生成成功代替。

## 3 阶段 0 冻结范围和统一契约

### 改动范围与交付物

- 从 `docs/catalog/artifacts.ts`、`artifact-collections.ts`、`standalone-pages.ts` 核对入口，与 `packages/blocks/src/application` 的实际实现关联。
- 为每个入口记录：公共依赖、局部状态/图表实现、受控属性、业务回调、迁移阶段、保留差异、验收入口。
- 记录当前提交与工作区差异，保留其他进行中的修改；已有失败单列，不计为本轮新增失败，也不能据此免除本轮验收。
- 冻结四个试点及容量/用量示例的浅色、深色截图与关键交互，供后续对比。
- 形成下面两份契约；可以先作为本文的实施补充，不强制新增规范网站或配置框架。

### 状态契约

| 维度 | 统一规则 | 必须保留的区别 |
| --- | --- | --- |
| 业务状态 | 映射为文案、语义色、图标、活动指示 | `enabled` 不等于 `healthy`；`resolved` 不等于恢复正常 |
| 数据可用性 | 首次加载、可用、确认无数据、不可用分别处理 | 未请求、零值、缺失值不是同一状态 |
| 请求进度 | 初次加载与后台刷新采用不同反馈 | 刷新不应默认清空旧数据 |
| 数据新鲜度 | 过期数据保留标记与更新时间 | stale 可与 refreshing 同时存在，不压成互斥枚举 |
| 操作进度 | 按按钮、行、表单等实际作用域展示 pending/error | 不用一个全局 loading 锁住所有无关操作 |
| 分类标识 | 模型、供应商、部门使用分类色 | 不能让普通分类看起来像告警 |

已有组件可继续接收现有接口，由业务适配到共同展示规范。本阶段不要求全库统一属性名。

### 图表契约

- 分类颜色按稳定系列 ID 分配；排序、筛选和刷新不会使同一系列换色。分类与状态调色板分开。
- 明确 X 轴时间戳/类别、时区、Y 轴单位、范围、是否包含零、堆叠方式和比较口径。不要对不同数据强制相同轴范围。
- 新的通用趋势预设默认保留缺失断点；已有 `connectNulls` 行为逐图登记，迁移时显式保留或作为单独的行为修正说明。
- 数值为零显示零；null、非法数值、无采样显示未知。禁止公共组件偷偷将非法输入全部补成零。
- 计数/容量拒绝负值；允许负值的差额类图表明确开启。不得一刀切裁剪所有负数。
- 分布百分比与容量占用百分比使用不同分母；超额文本显示真实值，图形如何裁剪必须明确。
- 空数据、全零、单点、缺失点、超大值都定义显示方式。Tooltip、图例与汇总使用同一单位。
- 沿用现有字号、surface、border、focus token；固定默认网格、线宽、圆角、图例标记和密度档位，允许有理由的覆盖。
- 信息不可只靠颜色或悬浮获取；交互图支持键盘或等价的可访问数据入口。刷新和减少动态效果模式不依赖连续动画表达状态。

### 阶段验收

- [ ] 44 个入口都有“迁移 / 已复用 / 保留领域实现 / 不适用”的初步结论。
- [ ] 每一种正常、警告、失败、未知、运行中的视觉映射有样例；业务文案与领域状态仍可追溯。
- [ ] 首次失败与刷新失败、空结果与筛选无结果、未知与零的规则无歧义。
- [ ] 每张拟迁移图已记录单位、缺失值与汇总口径，不能只记录外观。
- [ ] 基线截图、关键交互和已有失败留档，当前工作区修改得到保留。

## 4 阶段 1 状态组件和数据反馈

### 实施内容

1. 复用 `Badge.status` 并补充 `plain` 变体，用于无背景的圆点、图标和短文案；活动与长文案直接使用 `InlineNotice`。业务枚举由调用方映射。
2. 领域映射留在所属 Block。同一业务实体在列表、详情、图表图例中的含义保持一致。
3. 复用 `Empty` 表达确认的空结果，复用 `InlineNotice` 表达局部反馈；首次失败与重试直接组合 `Alert`、`AlertTitle`、`AlertDescription`、`AlertAction`。
4. 后台刷新、旧数据提示优先用现有组件组合；只有多个消费者需要相同结构时再抽 `DataStateNotice`，不先创建万能状态边界组件。
5. 先在集群列表、监控告警验证业务状态；在 Gateway Overview、Project Monitor 验证数据状态。

冻结方案时 `Badge` strong 变体不支持 status。第一批保留已有 strong 调用并在台账标记；阶段五已补齐对应前景/填充 token、对比度验证与 strong/status 能力，后续又补入 plain 与图标替换，状态边框采用 28% 不透明度。不能靠类型断言绕过限制，也不能仅为消除 color 属性而改变告警强调级别。

### 交付物

- 状态表现组件及指南，领域映射样例。
- 初次加载、刷新、首次错误、带旧数据的错误、空结果的演示用例。
- 试点采用记录、行为测试、主题截图及新增公共组件的 Registry 定义。

### 可验收内容

- [ ] 同一领域状态在试点页面中颜色、图标、文案一致，标签长度变化不会挤坏布局。
- [ ] 首次加载只显示对应骨架，不闪现“暂无数据”；后台刷新保留已有数据。
- [ ] 首次失败显示错误与可用的重试入口；刷新失败保留允许保留的旧数据并作提示。
- [ ] 确认无数据和筛选无结果文案不同；清空筛选触发正确回调。
- [ ] 错误不再伪装为 `Empty reason="no-data"`；不为静态状态批量增加 alert/live region。
- [ ] pending 防止重复提交，失败后可以重试；无关操作不被无理由禁用。
- [ ] 受控值只通过宿主更新，回调次数及参数与迁移前一致。
- [ ] 新增原语独立安装、编译通过；浅色、深色、键盘和窄容器检查通过。

退出条件：业务状态与数据状态两类试点都通过。不能仅凭组件演示页正确就进入全量替换。

## 5 阶段 2 图表与用量可视化

### 实施内容

| 能力 | 实施方式 | 首批消费者 |
| --- | --- | --- |
| 调色与格式化 | 在 Chart 底座扩展分类系列映射；按单位提供纯格式化工具，显式传入 locale/时区 | Gateway、Project Monitor |
| 图例 | 增加 `ChartLegend`，共用标记、名称、数值和可选占比；交互图例必须明确显隐行为 | 服务分布、费用归属、资源状态 |
| 趋势 | 优先抽轴、网格、Tooltip 和样式预设；由两处真实消费验证后形成薄的 `TimeSeriesChart` | Gateway 请求趋势、Project Monitor 请求趋势 |
| 圆环 | 抽取中心内容、轨道和分布绘制，候选名 `DonutSummary`；汇总由业务输入 | Resource Status All、服务/费用分布 |
| 分段条 | 抽取 `SegmentedBar` 视觉；容量进度和分类分布提供明确的不同模式/包装 | Storage Usage、Credit Usage、Resource Metric List |

不要求这些候选名全部成为独立公共导出。若仅用现有组件的共享配置即可消除重复，记录该选择；至少两个不同消费者验证后再固定公共 API。

保留 `MetricCard` 的轻量图实现与当前最低有效点数契约，不拿它替代完整趋势图。保留 `TimeRangeHistogram` 的选择/拖拽引擎，仅统一适用的颜色、提示与数据契约。P50/P95/P99 条形比较与延迟直方图语义不同，可共享颜色和格式，不能合并数据模型。

补入范围的 Security Overview 包含趋势、评分圆环及雷达图。趋势与圆环参与公共能力评估；雷达图先采用共享颜色、Tooltip 和可访问数据规范，保留专用绘制，不因仅一个消费者就新增通用雷达组件。扫描进度与安全评分必须分别表达，扫描完成后等待新快照的过程不能显示为数据已更新。

### 数据验收用例

| 输入/操作 | 预期 |
| --- | --- |
| 空数组、全零、单个点 | 三种状态有明确且合理的展示，不出现 NaN、Infinity 或伪造趋势 |
| 序列中间缺失 | 按登记策略留断点或连接；汇总不会未经说明将缺失当零 |
| 系列重排、筛选后恢复 | 同一系列颜色不变，图例与图形一致 |
| 金额、Token、毫秒、比例 | 汇总、轴、Tooltip 一致；0.15 与 15% 的转换有显式契约 |
| 总数大于已分配量 | 剩余或未覆盖部分明确展示，不能自动归为正常 |
| 用量超过容量 | 数字保留真实超额，图形不溢出，辅助说明准确 |
| 部分来源缺失 | 保持“不完整/未知”提示，不伪装为完整百分比分布 |
| 时间范围、时区变化 | 时间标签与实际数据窗口对应，不能仅更换标题 |

### 阶段验收

- [ ] Gateway 与 Project Monitor 的趋势采用共享能力，边距、网格、Tooltip 和格式符合契约。
- [ ] 至少两处圆环和两处分段条完成真实采用；其他场景有迁移结论。
- [ ] 上表每个适用数据用例有行为断言；数据总计与业务汇总一致。
- [ ] 原本固定的资源状态图能在约定容器内稳定显示；无需将所有小图强行改为同一尺寸。
- [ ] 图例长名称可换行或有可访问完整名称；Tooltip 不被页面容器裁剪。
- [ ] 键盘可检索数据或有等价数据入口；鼠标悬浮不是唯一取值方式。
- [ ] 浅色/深色及减少动态效果模式通过；调整窗口和侧栏时尺寸能正确更新。
- [ ] 公共依赖仍按需安装，安装普通状态组件不会额外引入图表依赖。

## 6 阶段 3 完整页面试点验收

试点用于发现组合问题，不再新增第二套组件 API。若发现抽象不适合第二个消费者，先缩小或修正抽象，再继续迁移。

| 页面 | 验收路径 | 必须保留的行为 |
| --- | --- | --- |
| Project Monitor | 概览 → 切换时间范围 → 存储 → 报告 → 刷新/错误 | 受控 tab/range、统计一致、未知值、旧数据提示、复制反馈 |
| AI Gateway Overview | 改时间窗口 → 检查请求/费用/延迟 → 刷新 → 失败重试 | 单位和时区、回调、旧数据保留、图表系列颜色 |
| Cluster Environment List | 状态筛选 → 搜索 → 组织切换 → 折叠导航 | 健康与新鲜度分别表达，筛选结果和导航行为不变 |
| Monitoring Alert List | 严重程度筛选 → 分页 → 查看处置记录 → 处置/静音回调 | 已处置与告警等级分别表达，分页及业务回调正确 |

### 阶段验收

- [ ] 四个页面走完上述路径，具有通过/失败/不适用记录与截图。
- [ ] 页面级、面板级、按钮级 loading/error 不重复宣告同一错误，也不互相覆盖。
- [ ] 布局容器职责明确：页面、内容面板、图表不重复加背景和边框。
- [ ] 关键按钮、筛选和 tab 能通过键盘操作；抽屉/弹层关闭后焦点合理返回。
- [ ] 从试点总结的公共 API 没有页面名称专用参数；必要业务差异由适配层处理。
- [ ] 实际跑通新增能力的 Registry 安装路径，而非只通过 workspace import。

退出条件：四个页面全部通过；未通过时留在试点阶段，不以继续迁移来掩盖问题。

## 7 阶段 4 工作区外壳和高频组合

已实施，具体范围、自动验证和人工验收清单见 [阶段四记录](./2026-10-06-block-page-unification-stage-four.md)。

### 实施内容

- 抽取业务层 `OperationsWorkspaceShell`，统一 ZAIops 的组织身份、主导航、服务导航、诊断会话入口、搜索入口、账号区和移动侧栏。
- 页面通过配置与插槽提供 active item、链接/回调、组织数据和搜索内容。Next 路由绑定放在适配层，不扩散到通用 UI 原语。
- 六个页面逐一采用：Operations、Cluster Environment List、Cluster Environment Detail、Inspection Report List、Monitoring Alert List、Service Management。
- 优先复用现有 `DataTablePagination`。两处手写分页如无法直接采用，则抽取无业务依赖的分页展示，并保留各自数据控制。
- 模型身份、行操作等仅在确认共同契约后抽取；现有 `InfoItem`、`DetailList` 能解决的布局直接采用。
- 明确 `Card`、`Container` 与页面 section 的使用边界；不继续增加只修改 padding 的同义面板组件。

### 阶段验收

- [ ] 六个页面共用同一套工作区结构，局部不再复制组织切换、搜索快捷键注册和导航骨架。
- [ ] 页面切换激活项正确；每次快捷键只打开一个搜索入口，没有重复监听行为。
- [ ] 展开、折叠、移动抽屉下，导航和账号操作都可访问，长名称不会遮挡操作按钮。

## 10 统一的浏览器验收矩阵

为控制工作量，采用“公共能力完整矩阵 + 每个入口核心路径”的方式，不要求所有页面机械遍历所有组合。

| 对象 | 必查组合 | 证据 |
| --- | --- | --- |
| 新增/修改公共原语 | 浅色与深色；短/长文案；全部公开状态；键盘；减少动态效果 | 行为断言和代表截图 |
| 四个试点页面 | 390、768、1440 CSS px；浅色与深色；核心路径；loading/error/empty/旧数据 | 浏览器记录和截图 |
| 图表/状态可嵌入 Block | 320、480、800 CSS px 容器；长图例；空/零/缺失/超额 | 尺寸与数据断言、代表截图 |
| 其他迁移入口 | 至少桌面与其声明支持的最窄视图；核心路径；受影响状态 | 单项通过记录 |
| 独立消费者 | 实际安装 CSS；主题切换；容器变化；状态与图表交互 | 独立环境与安装版本记录 |

通过标准：页面外层无意外横向溢出；表格/画布确需横向滚动时限制在声明容器内，关键操作仍可达；图形、图例和 Tooltip 不重叠或截断；状态不只靠颜色；焦点可见；禁用和 loading 不造成不可恢复状态。数据图与状态标记在相应背景上的可读性需实际检查，不能仅凭 token 名称认定通过。

### 独立消费者

目前 `test:consumer:styles` 的组件列表主要限定为 Button，不能作为图表和状态视觉通过的证据。实施必须扩展现有消费者/浏览器 runner，或新增有文档、可重复运行的验收入口；不得只在方案中假设已有覆盖。

现有脚本支持按组件指定 Next/Vite 消费者。例如，先验证已有试点：

```sh
ZERON_CONSUMER_COMPONENTS=project-monitor-01,ai-gateway-overview-01 ZERON_VITE_CONSUMER_COMPONENTS=project-monitor-01,ai-gateway-overview-01 pnpm test:consumer:smoke
```

该命令只作为安装/编译入口，不代替运行时视觉和交互验收。新增公共组件确定名称并登记后，将其加入同类定向安装检查；最终按影响范围使用 `pnpm test:consumer:all`，并显式补齐 Vite 目标列表，不能假定 all 会自动覆盖所有 Vite 目标。

### 必须新增的验证能力

- 状态转换：首次失败、刷新失败保留旧数据、过期时刷新、受控切换、防重复操作。
- 图表数据：零/未知区别、断点策略、单位换算、颜色稳定、容量超额、汇总一致。
- 组合行为：工作区快捷键只触发一次、导航激活、移动侧栏焦点、分页越界。
- 浏览器展示：主题、容器变化、Tooltip/图例布局和关键键盘路径。

仓库已有部分 contract 测试依赖源码字符串。抽取组件时应保留导出/安装类契约，将受重构影响的实现细节断言改为行为断言；不能仅删除失败断言，也不能为了保住字符串测试而保留重复代码。

## 12 提交边界和回退方式

下面是方案冻结时的原则性分组。六阶段实现及后续组件收敛完成后的实际提交顺序、文件与改动片段归属，以 [最终 9 笔 Commit 计划](./2026-10-06-block-page-unification-review-commit-plan.md#3-推荐-commit-顺序) 为准。

| 提交组 | 内容 | 回退策略 |
| --- | --- | --- |
| 规范与基线 | 台账、规则、验收用例 | 无运行时代码影响 |
| 状态公共能力 | 原语、试点、Registry、指南、相关测试 | 先回退试点采用；新增原语可暂时保留 |
| 图表公共能力 | 预设与复用图形、试点、安装依赖和验证 | 按消费者回退；保持旧导出直至迁移完成 |
| 工作区外壳 | 共享外壳与六页分批采用 | 页面逐项回退，避免必须整体回滚 |
| 其余迁移批次 | 每个业务组的采用与局部清理 | 独立回退该业务组 |
| 最终交付 | 文档、分发产物和验收记录 | 产物与源码版本一起恢复，不能混用 |

回退不覆盖用户其他未提交工作。不要为临时迁移增加永久 feature flag；只有真实运行需要双版本时才单独设计兼容策略。
