# Swap to Zeron UI 实施计划

日期：2026-09-18

状态：首版实现已落地，处于消费者样例验证阶段；尚未发布 npm，也未完成真实业务项目试点。

目标：新增 `swap-to-zeronui` skill，让 Agent 能把指定应用范围内的旧 UI 体系迁移到 Zeron，保留业务能力，并提供完整性与验证证据。

### 当前实施进度

| 阶段 | 状态与交付 |
| --- | --- |
| M0 | 已建立完成契约、版本化 schema、报告模板与 Next/Vite 迁移前样例 |
| M1 | 独立 skill 与 builder 交接规则已实现；已实际执行样例迁移并发现、修复安装布局问题 |
| M2 | 本地 CLI 已支持只读 scan/check，涵盖引用、残留、证据失效、例外及安装布局预检 |
| M3 | 两类样例自动化验证、恢复测试和安装回归已执行；真实项目试点、完整来源核对仍待完成 |
| M4 | 成套分发、官网提示词安装区、Markdown 安装入口、版本化 ZIP 与校验清单、CI 已实现并本地验证；公开发布尚未执行 |

当前新增命令仅指仓库源码和本地打包产物，不代表同版本 npm 包已包含这些功能。辅助恢复模块没有暴露自动迁移或恢复命令。样例自动化会有意将人工审查项标为 unchecked，不把浏览器测试通过直接等同于全项目完整迁移。

具体实施记录与验证边界见 [首版实现报告](2026-09-18-swap-to-zeronui-implementation.md)。下文保留原阶段定义作为验收依据。

## 1. 产品目标与完成定义

用户可以说：“把这个项目完整替换成 Zeron UI，保留原来的业务功能。”Agent 随后完成盘点、映射、安装、调用适配、主题与布局迁移、清理及验证，持续记录进度。

“完整”指冻结的迁移范围内：

- 基础控件、通用交互、导航、页面布局及视觉主题使用 Zeron 的公开能力。
- 路由、数据请求、表单验证、权限判断、持久化状态和业务操作语义保持有效。
- 原有 UI 实现不再被目标范围引用；无用途的旧依赖、Provider、主题样式已清理。
- 页面和关键状态均有核对结果，关键流程有运行验证证据。
- 没有未解决的能力缺口、未知引用或必需但未执行的检查。

以下内容可以保留，不能简单作为“不纯 Zeron”的判据：普通 HTML、局部布局元素、路由和状态库、领域逻辑、由 Zeron 组成的业务组件、Zeron 自身依赖的底层库。

专业编辑器、地图、图表引擎等必须逐项分类。若其自带旧 UI 且属于迁移范围，保留即构成例外；若仅为底层引擎而 UI 已由 Zeron 承担，可以保留。不能靠重命名组件或修改分类获得“完整”结论。

最终结果使用三个明确标签：

| 结果 | 条件 |
| --- | --- |
| 完整迁移并验证 | 全部完成门槛通过，无范围内例外、未知项或关键未验证项 |
| 迁移完成但保留例外 | 例外已明确获用户接受，其余门槛通过；不能称为完整替换 |
| 部分完成／待验证 | 仍有阻塞、失败、未处理项或关键检查未执行；列出后续行动 |

明确指定页面或目录时，完整性只针对该范围。不得把局部迁移称为全项目完成，也不得在结束前缩小范围来提高完成率。

## 2. 当前仓库基础与约束

以下为本次源码检查结果，不代表已重新运行所有测试。

| 已有资产 | 当前能力 | 本计划如何利用 |
| --- | --- | --- |
| `.agents/skills/zeron-page-builder/` | 组件选型、布局契约、业务适配、安装与验证 | 作为共享实现规范 |
| `packages/ui/registry.json` | 75 个 `registry:ui` 条目，另有主题、lib、hook | 按实际 API 建立目标清单 |
| `packages/blocks/registry.json` | 36 个 Block 与 1 个 component 条目 | 仅在任务和集成接口匹配时复用 |
| `packages/cli/src/cli.js` | init、add、list、view、doctor | 复用安装链路，不另造复制源码安装器 |
| `packages/cli/src/install-plan.js` | 依赖闭包、目标路径、文件冲突、安装前哈希 | 复用安装预检，补充迁移级检查 |
| `scripts/create-registry-release.mjs` | 生成带 release manifest 的本地不可变候选 | 固定迁移来源；本地生成不等于已公开发布 |
| `packages/lint/` | 设计静态检查，当前为私有工作区包 | 已接入时使用；不能假设外部可 npm 安装 |
| `scripts/test-consumer-installs.mjs` | 独立消费者安装与构建测试 | 保留安装回归，与迁移测试分开 |
| `docs/agent-guides/` | 5 份组件指南、8 份 Block 指南 | 优先使用；其余依靠源码与类型补齐证据 |

当前限制：

1. Registry 元数据要求 React 19、Tailwind 4，部分 Block 要求 Next.js。当前 CLI 并不完整校验所有实际解析版本，迁移预检需要核实已安装版本及锁文件。
2. `add --overwrite` 覆盖安装计划内文件，不会改写调用方属性、事件和业务逻辑。
3. `doctor --check` 检查安装记录和文件存在性，不证明文件未被修改、组件调用正确或迁移完整。
4. 安装记录尚不足以提供全面的来源、内容完整性和迁移回退保证；迁移状态需要独立记录。
5. 当前 skill 默认保留已有 shell。完整迁移模式需要区分“保留导航行为和路由”与“允许替换旧 shell 的实现”。
6. 已有消费者测试主要验证安装，不等于验证旧项目迁移。必须增加专门样例。

## 3. 第一版支持范围

### 3.1 支持策略

| 维度 | 第一版承诺 |
| --- | --- |
| 技术栈 | React 19、Tailwind 4、TypeScript/TSX |
| 框架 | Next.js App Router；Vite React 的页面迁移，路由范围需要显式清单或可验证配置 |
| 包管理器 | npm、pnpm；保持项目原有工具及锁文件 |
| 来源 | 已识别版本与本地定制的 shadcn 风格组件，以及普通 React/Tailwind 自建控件 |
| 页面 | 应用导航、列表、详情、表单、设置、常见弹窗 |
| 主题 | Zeron 语义体系与控件行为；保留可通过公开主题能力表达的品牌配置 |
| 执行方式 | Agent 执行迁移；确定性工具负责盘点、前置条件和残留检查 |

这是计划验证的支持矩阵，只有相应样例通过后才能对外标记为已支持。不能因为存在 React Registry 元数据，就推断所有 React 框架或 Block 均已通过迁移验证。

### 3.2 第一版不承诺

- 自动升级 React、Tailwind 或迁移应用框架。
- 通用支持 Ant Design、MUI、Chakra 等全部组件和交互；可以分析缺口，后续逐个建立来源映射。
- 完全无人判断的任意项目一键转换。
- 像素级保留旧设计；保留的是业务语义与信息结构，视觉向 Zeron 收敛。
- 自动完成后端、认证、计费等业务重构。
- 增加通用转换插件平台、可视化迁移管理后台或统一组件包装层。

不支持的情况先输出具体差异和可迁移部分。只有用户意图未覆盖的范围扩大、产品取舍或破坏性操作需要提问；普通映射、已授权文件替换和业务适配不反复确认。

## 4. 交付结构与职责

新增独立 skill，现有 builder 继续负责页面实现。两者复用契约，避免维护两套相互矛盾的规则。

```text
.agents/skills/swap-to-zeronui/
  SKILL.md
  agents/openai.yaml
  references/
    scope-and-completion.md
    inventory-and-mapping.md
    migration-workflow.md
    verification-and-recovery.md
    source-profiles/shadcn.md
  assets/
    migration-plan.schema.json
    report-template.md

packages/cli/src/swap/                 # 第二阶段新增
  scan.js
  check.js
  project.js
  state.js

packages/cli/tests/swap/               # 第二阶段新增
  scan.test.js
  check.test.js
  state.test.js

tests/fixtures/swap/                  # 根据现有测试目录约定落位
  next-shadcn/
  vite-custom/
scripts/test-consumer-migrations.mjs  # 消费者迁移集成测试
```

职责边界：

- **Skill**：理解用户范围、制定映射、编辑业务调用、处理组合与缺口、执行验证、输出报告。
- **Builder 共享规则**：组件语义、结构、样式边界、公开 API 与业务适配。
- **CLI scan/check**：只做可重复的事实收集和静态检查，不做业务语义承诺。
- **Registry 与安装器**：安装组件及其依赖，不承担业务迁移。
- **浏览器和项目测试**：证明产品行为与渲染结果；不能被静态检查代替。

Skill 分发必须同时包含 builder 及其引用文件，或通过明确依赖安装它。不得发布含失效相对链接的单独 skill。开发时先用配套目录，发布前验证完整复制后的可用性。

## 5. 迁移工作流

### 步骤 A：确定范围与基线

1. 读取目标项目指令、技术栈、包管理器、实际依赖版本、别名、CSS 入口和已有 Zeron 安装。
2. 检查工作区未提交改动，记录本次相关文件的原始内容和哈希；不覆盖用户既有改动。
3. 确定路由、页面、公共组件和样式范围；局部迁移同时记录共享模块对范围外页面的影响。
4. 记录现有类型、构建、业务测试结果及代表页面截图。现有失败需保留证据。
5. 固定 CLI 版本、Registry release、清单摘要和读取到的组件 API。使用可用的不可变发布地址，或受控本地快照。对照相同版本、配置与别名下的干净安装结果核对 managed 文件，不能把已有消费者文件自行取哈希就当作官方基线。

产出：范围清单、兼容性结论、基线、未决问题。若只拿到可变在线 Registry，可先做扫描，但不能把未固定来源当作可复现的安装基线。

### 步骤 B：盘点旧体系

扫描对象包括：

- 直接导入、别名导入、重新导出、共享业务包装组件、静态动态导入。
- 页面与布局文件、路由注册表、公共 Provider、Portal、主题切换、字体和图标。
- 自建 button/input 等交互实现、旧设计 token、CSS modules、全局选择器及内部节点覆盖。
- loading、empty、error、disabled、permission、overflow 等状态。
- 对话框、抽屉、菜单、Toast 等只有交互后出现的界面。

Next App Router 基于路由文件建立清单，包含 layout、loading、error 等影响界面的文件。Vite 不等于存在统一路由约定，需要结合实际配置、入口引用及人工核对。

非字面量动态引用、无法解析的别名、运行时路由、复杂 prop spread 标为 `unknown`，不可静默忽略。扫描原生 HTML 只是候选发现，不能见到 button/div 就判违规。

### 步骤 C：建立映射与缺口

每项映射使用四类结果：

| 类型 | 含义 | 动作 |
| --- | --- | --- |
| direct | 已验证公开 API 和行为可对应 | 替换调用并验证 |
| adapt | 属性、事件、值类型或数据接口不同 | 添加最小业务适配 |
| compose | 需要多个 Zeron 组件实现原任务 | 重新组合并保留业务语义 |
| gap | 公开能力不足或证据不充分 | 明确缺口与处理路径，不制造假支持 |

每条记录应包含来源组件及证据、目标 Registry item、所有调用位置、属性与事件映射、数据／路由约束、依赖、验证场景和状态。

第一批映射覆盖：Button、Input、Textarea、Checkbox、Switch、Select、Combobox、Dialog、Popover、Dropdown、Tabs、Table/DataTable、Tooltip、Toast、Field，以及 AppShell/PageLayout/Sidebar/TopNav。

具体规则示例：

- Button 依据操作层级映射 variant；不能把所有旧 default 或 outline 不加判断地统一映射。
- 旧图标尺寸形式转为 Zeron `iconOnly` 与合适的 control size，保留 aria-label。
- Select 的值、回调、必填状态和复合结构分别检查；多选或远程搜索先评估 Combobox。
- 表格保留稳定 row id、服务端分页、排序筛选参数、选择范围和异步状态；不能换成演示数据。
- Dialog 检查受控 open、提交后关闭、焦点恢复、嵌套浮层与 Portal 主题。
- 原有表单库及校验逻辑可继续使用，通过公开事件和字段属性连接。

来源映射必须注明测试过的版本或源码特征。本地已定制的同名 shadcn 文件按实际源码处理，不能仅凭目录判断兼容。

### 步骤 D：安装与按批替换

默认按依赖顺序：基础主题和 Provider → 公共控件及其调用方 → 应用 shell → 页面布局 → 表单／数据／浮层流程 → 其他页面。可以调整顺序，但每批应形成可验证的完整单元。

安装与冲突规则：

1. 使用现有 CLI 解析完整依赖闭包，检查全部目标文件，不只检查请求的那个组件。
2. 对冲突文件读取内容、识别原有定制并迁移相关调用；把目标文件分成保留、替换、删除、待判断。
3. 现有 `--overwrite` 是整次安装选项，不能当作逐文件授权。仅当该批闭包内全部冲突均有明确处理方案，才执行该批覆盖安装。
4. 需要查看有冲突的计划时，可利用当前只读 `--dry-run --overwrite` 行为；执行写入前仍须重新校验文件与计划一致。
5. 当前 dry run 不完整展示 package/lockfile/CSS 的最终变更。首次迁移样例应在可恢复工作副本验证安装副作用，并将这些文件纳入快照与差异审查。
6. 执行前重新检查相关文件哈希。如果用户在计划后修改了文件，重新分析或合并，不应用陈旧覆盖计划。
7. 安装后记录实际 diff、组件来源和已验证版本；对业务调用及静态／运行检查进行修复。

不要为解决冲突复制出第二套同名职责的基础组件。临时兼容桥仅用于必要的分批切换，记录所有引用与移除条件；最终不能依靠桥中的旧 UI 宣称迁移完成。

### 步骤 E：迁移主题与布局

- 将旧 token 按前景、背景、状态、边框、焦点、表面层级等语义映射到 Zeron。
- 品牌配置通过公开主题入口处理；避免业务代码覆盖 Zeron 内部状态样式。
- 保留 URL、导航层级、权限、折叠与选中行为；在完整模式下允许替换旧 shell 实现，禁止嵌套重复 AppShell。
- 明确每个页面的滚动归属、固定区域、窄屏导航和长内容表现。
- 对 Portal 中的 Dialog、Popover、Select 单独检查主题、层级和暗色模式。
- 临时共存阶段检查全局 reset/token 冲突；不要假设外层主题 wrapper 能覆盖 Portal。
- 若共享主题不能安全局部接入，重新划分可独立验证的迁移批次，或报告需要扩大的影响范围。

### 步骤 F：清理和最终核对

1. 重新扫描完整目标范围和受影响的共享调用方，对照原清单逐项核销。
2. 按实际引用清理旧实现、CSS、Provider、资源和直接依赖；区分直接使用和必要的传递依赖。
3. 检查动态引用、重新导出、旧主题选择器及临时兼容桥。
4. 重跑受影响的产品流程与构建，在清理后验证锁文件安装可复现。
5. 输出最终报告；保留例外、unknown 或关键 unchecked 时使用对应的不完整结论。

## 6. 状态文件与恢复

消费者项目建议使用：

```text
.zeron/migrations/<migration-id>/
  plan.json
  report.md
  evidence/       # 截图和检查结果，按项目规则决定是否入库
```

第一版只使用一个版本化 `plan.json`，避免多份状态彼此失步。主要字段：

| 字段 | 内容 |
| --- | --- |
| schemaVersion、id、status | 格式版本、迁移 ID、整体状态 |
| scope | 应用根目录、目标路由／文件、明确排除项、共享影响范围、初始范围摘要及变更记录 |
| baseline | git revision（可用时）、相关文件原始哈希、迁移前检查证据 |
| source | CLI 版本、Registry release、来源与清单摘要 |
| inventory | 路由、组件、Provider、样式与依赖事实，以及 unknown |
| mappings | 来源→目标、direct/adapt/compose/gap、调用位置与适配要求 |
| batches | 批次依赖、文件操作、前后哈希、恢复快照索引、状态 |
| checks | 命令或人工步骤、范围、结果、时间、对应源码哈希与证据位置 |
| exceptions | 缺口、原因、实际影响、用户接受记录与后续方案 |

组件项状态：`pending → mapped → migrated → verified`；证据不足或能力缺口转为 `blocked`。仅安装成功不能成为 `verified`。

检查状态统一为 `passed / failed / unchecked`。相关文件、配置或依赖改变后，旧检查证据失效，需要重新执行受影响检查。未知 schemaVersion、缺字段或不存在的证据不能默认为通过。

初始范围同时保存在迁移前报告或版本历史中，范围调整记录原因和用户指令依据。工具可校验已保存的摘要及重新扫描源码，但本地可编辑的 plan 不是防篡改凭证，最终仍需审查范围与报告的一致性。

恢复策略：

- 每批记录修改前内容、文件是否原先存在以及修改后哈希；包含 package.json、锁文件、CSS 和安装状态文件。
- 原始快照存放在项目外的本地恢复目录，只保存本次涉及的源码／配置，避免扫描或复制凭据及无关文件。
- 恢复前检查当前内容是否仍等于该批修改后版本，存在用户后续编辑时进行合并处理，不直接覆盖。
- 只恢复该批产生的改动，不使用全项目 hard reset，也不删除用户新文件。
- 中断后重新核对源码、安装状态和验证证据，不能仅依赖状态标签继续。
- 恢复保证覆盖工作区文件和依赖清单；外部服务副作用不纳入 UI 迁移，依赖安装过程也不能被描述为全局事务。

## 7. 辅助工具的最小设计

以下命令已在第二阶段的本地源码中实现；消费者仍须检查实际安装的 CLI 帮助，不能假设 npm 上的版本已经可用。

```text
zeron-ui swap scan --cwd <project> --json
zeron-ui swap check --cwd <project> --plan <plan.json> --json
```

不新增自动 `apply` 引擎。Agent 负责源码迁移，避免在第一版实现高成本通用 codemod。

### scan

- 默认只读，输出 JSON 到 stdout；日志走 stderr，不主动安装包或写入文件。
- 复用 CLI 已有 TypeScript 依赖进行 AST 分析和模块解析；发现失败保留 diagnostics。
- 收集依赖、别名、静态导入／重新导出、JSX 使用、路由候选、样式入口和动态未知项。
- 排除 node_modules、构建产物、缓存与生成目录；工作区多应用必须选定目标应用，不能合并为一个未定义范围。
- 支持 TypeScript 配置及已验证的组件别名；不支持的路径映射明确返回 unknown。
- CSS 搜索是线索，语义 token 是否正确仍由规则和 Agent 判断。

### check

- 根据冻结范围、迁移清单和最新源码重新检测旧引用、待处理项、失效证据及文件漂移。
- 区分残留旧 UI、底层引擎、业务组合及范围外引用；输出理由和位置。
- 检查证据是否存在并对应当前源码，但不声称独立证明人工记录的真实性或业务等价。
- 不接管现有 doctor，不把“文件存在”升级为迁移通过。
- 输出 `staticStatus` 与 `completionStatus`；前者通过不能单独代表后者通过。

建议退出码契约：scan 为 0=扫描执行完成、1=不可读取或内部失败、2=不支持的配置／不完整解析；结果仍保留 unknown 明细。check 为 0=静态门槛通过、1=失败或残留、2=未验证／不支持。非零退出不影响输出已获得的诊断。

## 8. 验收与测试矩阵

### 8.1 单次迁移完成门槛

- 冻结范围内路由与 UI 清单已逐项处理，没有 pending、blocked 或 unknown。
- 没有未解释的旧 UI 导入、重新导出、全局样式引用或临时桥。
- Zeron 组件基于可信来源安装，消费者未擅改 managed 内部实现；业务适配位于项目代码。
- 能力缺口已补齐；有接受的保留例外只能给“保留例外”结果。
- 类型与生产构建通过；如基线已有失败且仍未解决，最终检查仍为失败，报告可注明未引入新失败，但不能称完全验证。
- 必需业务场景通过，重点覆盖提交／校验、查询参数、分页排序、选择、权限与错误反馈。
- 所有范围内页面至少完成可访问与渲染核对；动态路由覆盖代表性参数及相关权限分支。
- 代表性窄屏与宽屏、明暗主题（项目支持时）、长文本、键盘焦点及浮层验证通过。
- 清理完成后安装与构建仍可复现，未影响范围外消费者。

design lint 已接入时必须执行；未接入时记录该自动化检查不可用，使用明确的契约审查与运行验证替代，不宣称 lint 已通过。若项目原有规范把 lint 定义为必需门槛，则不可跳过。

报告至少列出“已核对路由／范围内路由”“已验证映射／全部映射”“关键流程通过／全部必需流程”三个分子与分母，以及残留、unknown、例外数量。没有可靠分母时报告数量和缺失范围，不输出貌似精确的整体完成百分比。

### 8.2 工具单元测试

| 场景 | 必须验证的行为 |
| --- | --- |
| 直接导入、重命名、barrel export、别名 | 找到真实来源和调用关系 |
| 动态导入、运行时路由、无法解析的模块 | 不漏报为干净结果，生成 unknown |
| 无关 HTML、业务组件、共享依赖 | 不按名称直接误判旧 UI |
| 未知 schema、旧证据、文件在计划后变化 | 拒绝完整结论，要求重新核对 |
| 只读扫描 | 不改变消费者源码、package、lockfile、CSS |
| 已完成项目再次执行 | 不重复安装主题、不制造重复组件和映射 |

### 8.3 消费者迁移样例

| 样例 | 内容 | 必须证明 |
| --- | --- | --- |
| Next + shadcn 风格 | 列表、编辑表单、Dialog、Sidebar；具有同名组件定制 | 调用适配、主题／shell 替换、路由和服务端分页不变 |
| Vite + 自建 UI | 设置表单、选择器、Toast、主题切换 | 纯 React 组件可用，拒绝 Next-only Block |
| 未知与不支持输入 | 非字面量引用、React 18、Tailwind 3、非 React 项目 | 不兼容写入前识别，不误报完成 |
| 恢复及冲突 | 安装失败、修改到一半、用户追加编辑、共享依赖冲突 | 可恢复本批且保留用户修改 |

测试分三层：工具单测验证扫描与状态；固定迁移前后样例验证调用和产品行为；Agent 实际执行样例验证 skill 是否能从旧项目走到可验收结果。提交一份手工写好的迁移后样例不能替代第三层。

至少完成上述两个正向项目的 Agent 试运行，再选一个真实消费者项目试点。真实项目尚未指定，因此试点耗时与实际组件覆盖率不能提前保证。

## 9. 实施阶段与工作项

### M0：确定契约与验证样例

工作项：

- 冻结第一版支持矩阵、完成标签和范围规则。
- 建立最小 plan schema、报告模板及两个迁移前样例。
- 确定可用 Registry 版本与安装来源，记录未发布资源的本地替代方式。
- 给样例建立关键业务行为测试和迁移前截图。

验收：对同一个样例，迁移范围、业务不变量、预期 UI 与完成标准没有歧义。

### M1：独立 skill 原型

工作项：

- 创建上述 skill 主文件、references 和 agents/openai.yaml。
- 描述触发语：“swap to zeronui”“替换成 Zeron UI”“迁移整个项目到 Zeron”等。
- 复用 builder 契约；补充完整迁移时的 shell／主题替换规则，避免与 builder 默认保留逻辑冲突。
- 编写首批组件映射规则，所有属性以实际源码验证。
- 使用现有 CLI 和人工核对清单完成一个 Next 样例；验证中断后继续与报告输出。

验收：无需新扫描工具也能完成受限范围迁移，缺口被准确报告；不要求用户重复授权已明确的迁移操作。

### M2：确定性扫描与检查

工作项：

- 在 CLI 中新增 scan/check 命令分派与上述最小模块。
- 实现 AST 盘点、范围解析、unknown、残留检查和验证证据失效规则。
- 实现 schema 校验、只读输出与退出码契约。
- 增加对应工具测试，CLI README 清楚区分安装检查与迁移检查。

验收：测试矩阵通过，不能通过改清单标签隐藏源码残留；扫描不修改消费者文件。

### M3：完整迁移验证与恢复

工作项：

- 接入 Vite 样例，补齐有冲突安装、主题共存、Portal、暗色和窄屏场景。
- 验证闭包级覆盖、安装部分失败、恢复和重复执行。
- 完成 Agent 两个样例的全过程运行，保存耗时、失败点、人工决策和证据。
- 复用既有 consumer smoke，并新增 migration 集成脚本和适当 CI 检查。
- 选择一个真实项目试点，按出现的实际问题修正映射与支持范围。

验收：两个正向样例、负向与恢复场景均通过；真实试点给出真实结论，若未完整通过，公开支持范围不得扩大。

### M4：文档与分发

工作项：

- 增加仓库 README 使用入口，说明适用范围、实际安装方式、保留业务的约束和完成标签。
- 验证 skill 与 builder 成套分发，引用可用；如借助现有 skill 发布方式，沿用其约定。
- CLI 包形态测试验证新增文件和命令实际被打包。
- 在试点之后决定是否需要发布消费者可安装的设计 lint；不把它暗中塞入第一版必需范围。
- 准备发布变更说明；实际 npm 发布或对外部署按单独发布任务执行。

验收：全新消费者能按文档安装并复现支持样例；文档不引用未实现命令或不可安装的包。

## 11. 检查安排、估算与发布门槛

按修改范围运行检查：

- 仅文档／skill 变更：核对引用、文件打包、指令冲突、示例 API 与实际 Agent 样例；不为纯文字改动跑整个 UI 构建。
- CLI 变更：针对性 node 测试、现有 `pnpm cli:test`、`pnpm cli:check` 及相关消费者用例。
- UI／Registry 变更：对应契约测试、Registry 生成与 `pnpm registry:check`，运行受影响消费者安装测试和设计检查。
- 跨主题／shell 的迁移：受影响页面运行验证和生产构建，清理后再次验证必要项。

工程估算，按一位熟悉仓库的工程师顺序推进：

| 阶段 | 估算 |
| --- | --- |
| M0 契约与样例 | 1–2 人日 |
| M1 skill 原型 | 2–3 人日 |
| M2 扫描与检查 | 3–5 人日 |
| M3 自动化样例与恢复验证 | 3–5 人日 |
| M4 文档与分发 | 1–2 人日 |

合计约 10–17 人日，另加真实项目试点时间。该估算不包含 React/Tailwind 升级、复杂组件补库或新的来源框架支持；完成 M1 后应依据实测修订。

对外发布前必须具备：受限支持矩阵、可复现的组件来源、两个正向样例与负向／恢复验证、无效证据不误报完成、真实可用的分发路径。仅完成 M1 时可称“迁移 skill 原型”，不称通用完整替换工具。

## 12. 实施起点与后续演进

第一批执行 M0 和 M1：先建立范围与验收契约，创建独立 skill，并在 Next 样例上走完一次真实迁移。用这次结果确定扫描工具真正需要自动化的部分，再进入 M2。

后续演进依据真实迁移需求排序：扩展来源组件映射、发布消费者设计检查、加强可信安装完整性、添加经过验证的局部 codemod。每项新增能力都应附带迁移样例与反例，不提前建设通用转换框架。
